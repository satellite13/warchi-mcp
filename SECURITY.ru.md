# Политика безопасности

## Поддерживаемые версии

Исправления безопасности сейчас предоставляются на best-effort основе для актуального состояния ветки `master`.

## Как сообщить об уязвимости

Пожалуйста, **не** публикуйте уязвимости в открытых issue.

Вместо этого:

1. Подготовьте приватный отчёт, включив:
   - описание уязвимости
   - влияние/риск
   - шаги воспроизведения
   - возможную стратегию исправления
2. Передайте отчёт мейнтейнерам по приватному каналу связи:
   - private vulnerability/advisory report в платформе хостинга репозитория (предпочтительно), или
   - личное сообщение/email мейнтейнерам (`nikolay@groznykh.ru`).

Если приватный канал ещё не определён, создайте его перед публичным релизом и обновите этот документ.

## Рекомендации по безопасному деплою

- Относитесь к API-ключам как к секретам: показ один раз при создании, хранение только в конфиге MCP-клиента / secret store
- Завершайте TLS перед `warchi-mcp`; не выставляйте plain HTTP в публичный интернет
- Убедитесь, что reverse proxy передаёт `Authorization` / `X-Api-Key` и не логирует их значения
- Не логируйте API-ключи, JWT и полные заголовки `Authorization`
- Направляйте `AREPOS_BASE_URL` на доверенный arepos (по возможности private network / mTLS)
- Скомпрометированные ключи сразу отзывайте в профиле wArchi
- Минимальные права: `mode=all` с `models:read`, если запись не нужна, или `mode=grants` с read на большинстве моделей и write только где требуется
- Один секрет `warchi_ak_…` на агента; для смешанных прав по моделям используйте grants, а не несколько ключей
- Деактивация пользователя мягко блокирует exchange через `isActive` (ключи не отзываются автоматически — при необходимости отзывайте явно)
- Держите зависимости и base images обновлёнными
- Ограничьте сетевой доступ так, чтобы до MCP endpoint доходили только нужные клиенты
